# vdct

Installs [VisualDCT](https://github.com/epics-extensions/VisualDCT) into the
developer stage of a generic IOC container, so that support modules containing
VDCT `.vdb` files can be built from pristine upstream sources.

## Why

VDCT `.vdb` files are not understood by vanilla EPICS base, so a module that
ships them normally has to be forked and pre-converted (for example with
[vdct2template](https://github.com/epics-containers/vdct2template)) before it
can be built in a container. That fork then has to be re-made for every
upstream release. Installing VisualDCT removes the fork: point the module's
`version` at the upstream tag and the container build does the conversion.

## Usage

Add this before any support module that contains `.vdb` files:

```dockerfile
COPY ibek-support/vdct/ vdct
RUN ansible.sh vdct --tags system,pre_build_tasks
```

The `--tags` are required. VisualDCT is a tool, not a support module - there
is no repo to clone and no `make` to run, so the clone, release and build
phases of the standard ansible role must not run.

Then in the support module's `<module>.install.yml`, just use the upstream
version. No `.vdb` specific settings are needed - the build rules are picked
up automatically.

## What gets installed

| Path | Purpose |
| --- | --- |
| `openjdk-21-jre-headless` | via `apt_developer`, so developer stage only |
| `/usr/local/lib/vdct/VisualDCT.jar` | the 1MB binary jar from the release archive |
| `/usr/local/bin/flatdb` | wrapper invoking `com.cosylab.vdct.GenerateFlatDatabase` |
| `$(EPICS_BASE)/cfg/CONFIG_VDCT` | defines `FLATDB` and `FLATDB_FLAGS` |
| `$(EPICS_BASE)/cfg/RULES_VDCT` | `%.vdb` -> `%.template` rules |

The `cfg` folder is EPICS base's documented extension point: base includes
`<top>/cfg/CONFIG*` and `<top>/cfg/RULES*` for every top named in a module's
`configure/RELEASE`, and `EPICS_BASE` is always one of those tops. So no file
in base's `configure` folder is modified, and no support module needs patching
to pick the rules up.

None of this is registered as a runtime asset, so the runtime image is
completely unaffected. The cost is roughly 210MB in the developer image.

The flattener runs headless - no `DISPLAY`, no X libraries and no
`-Djava.awt.headless=true` are required.

## Build ordering

A `.vdb` file names the dbd it needs in a `#! DBD("...")` header, and that dbd
is usually generated by the module's own `src` directory. Under `make -j` base
only serialises subdirectories via `<dir>_DEPEND_DIRS`, so without help the
`Db` directory can start flattening before that dbd exists — VisualDCT then
prints `No DBD loaded! Exiting...` for every file.

**This is handled globally and needs no changes in the support module.**
`cfg/CONFIG_VDCT` finds every subdirectory containing `.vdb` files and makes it
depend on its sibling `*src*` / `*Src*` directories.

It has to live in `CONFIG_VDCT` rather than `RULES_VDCT`: base expands
`<dir>_DEPEND_DIRS` while `RULES_DIRS` defines the inter directory rules, and
`RULES_DIRS` never includes `RULES_FILE_TYPE`, so `cfg/RULES*` is not read at
the App level at all. `cfg/CONFIG*` is read there, via the `configure/CONFIG`
include at the top of the App Makefile, which is early enough.

The dependency is a deferred (`=`) assignment filtered against `$(DIRS)`, so a
source directory that exists on disk but is not part of the build is never
depended on, and modules with no `.vdb` files get no dependency at all.

If a module needs something more specific, the `Db` Makefile can still set
`VDB_DEPS` to a list of extra prerequisites for the flattening rule.

Note that VisualDCT exits 0 even when it gives up, so the `flatdb` wrapper
checks that output was produced. Without it the build reports only the
secondary error `mv: cannot stat '<x>.template'`.

## Validating the generated templates

When first converting a module - or after a VisualDCT version bump - it is
worth diffing the generated `.template` files against a build of the same
module tag made by a different VDCT harness, such as a site's traditional
build. Copy the installed templates out of the image and compare them with

- the `#! Generated by VisualDCT` stamp removed, since it carries the tool
  version
- absolute paths inside `# expand("...", name)` comments normalised, since
  VisualDCT canonicalises sub template paths against the build directory

Both are cosmetic. Anything left after normalising those two is a real
difference. This was done for dlsPLC 3-0-72 against the Diamond production
build and all 83 templates matched.
